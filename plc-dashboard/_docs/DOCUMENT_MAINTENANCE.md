# ドキュメントメンテナンスガイド

**作成日:** 2025-10-30
**最終更新:** 2026-01-19

## 目的

このガイドは、プロジェクトのドキュメントが常に最新で有用な状態を保つためのルールとベストプラクティスを定義します。

**重要:** このルールに従うことで、定期的なメンテナンスが不要になり、ドキュメントが自動的に最新状態を保ちます。

## 基本原則

### 1. コードと同時に更新
コード変更時にドキュメントも同じPRで更新してください。「後で更新する」は禁止です。

### 2. 必要最小限の更新
変更した箇所のみ更新してください。全体の書き直しは不要です。

### 3. _docs/を優先
詳細情報は`_docs/`に記録し、CLAUDE.mdは概要のみにしてください。

### 4. 古い情報は削除
更新よりも削除を優先してください。古い情報は価値がマイナスです。

## 更新が必要なケース

以下の変更を行った場合、**必ず該当ドキュメントを更新**してください：

| 変更内容 | 更新対象ドキュメント | セクション |
|---------|------------------|-----------|
| 新しいAPIエンドポイント追加 | `plc-dashboard/_docs/architecture/backend.md` | APIエンドポイントセクション |
| データベースモデル変更 | `plc-dashboard/_docs/architecture/database.md` | テーブル定義セクション |
| マイグレーション追加 | `plc-dashboard/_docs/architecture/database.md` | マイグレーションセクション |
| 新しいPLCメーカー対応 | `plc-dashboard/_docs/plc-knowledge/plc-manufacturers.md` | 対応メーカー表 |
| プロトコル実装追加 | `plc-dashboard/_docs/plc-knowledge/protocols.md` | 該当プロトコルセクション |
| 新機能追加 | `plc-dashboard/_docs/features/[機能名].md` (新規作成) | - |
| 設計判断 | `plc-dashboard/_docs/decisions/[判断内容].md` (新規作成) | - |
| 作業フロー変更 | `CLAUDE.md` (リポジトリルート) | `## 作業フロー` |
| 環境変数追加 | `plc-dashboard/_docs/deployment/environment-variables.md` | 該当セクション |

## 更新が不要なケース

以下の変更では**ドキュメント更新は不要**です：

- バグ修正（ロジック変更なし）
- コメント追加・修正
- リファクタリング（機能・API変更なし）
- テストコード追加
- ログ出力の変更
- 変数名変更（外部APIに影響なし）

## 更新フォーマット

### 1. ファイルパスと行番号を明記

```markdown
#### `backend/api/routes.py`
- **`POST /api/equipment/<equipment_id>/maintenance`** - メンテナンス記録保存 (routes.py:1234-1256)
```

### 2. 簡潔に書く

❌ 悪い例:
```
この機能は非常に重要で、多くの検討を重ねた結果、最終的にSQLiteベースの
ローカルバッファを採用することにしました。これにより...
```

✅ 良い例:
```
目的: オフライン時のデータロス防止
選択: SQLiteベースのローカルバッファ
根拠: 軽量、トランザクション対応、Pythonバインディング標準搭載
```

### 3. コード例を含める

重要な設計パターンはコード例で示してください。

## _docs/への追加基準

### 追加すべき（_docs/に記録）

- ✅ 設計判断 - 技術選択の根拠
- ✅ 新機能 - 機能の目的と実装ポイント
- ✅ PLC特有の知見 - プロトコル、エンディアン、トラブルシューティング
- ✅ アーキテクチャ変更 - システム構成の大きな変更
- ✅ デプロイ手順 - 環境構築、CI/CD設定

### 追加不要（CLAUDE.mdで十分）

- ❌ 日常的な開発コマンド
- ❌ 一時的な作業メモ
- ❌ 個人的なTODOリスト

## ディレクトリ構成

| ディレクトリ | 用途 | 例 |
|-------------|------|-----|
| `decisions/` | 設計判断の根拠 | なぜSocket.IOをthreadingモードにしたか |
| `architecture/` | システム構成・コンポーネント詳細 | frontend.md, backend.md |
| `features/` | 新機能の実装記録 | エラー・アラームシステム |
| `plc-knowledge/` | PLC特有の知見 | プロトコル、エンディアン |
| `deployment/` | デプロイ・運用手順 | 環境変数、ラズパイ設定 |
| `commands/` | 開発コマンド集 | よく使うコマンド |
| `setup/` | 環境セットアップ | MCP、CI/CD |
| `testing/` | テスト関連 | E2Eテスト、デバッグ |
| `history/` | 過去の記録（アーカイブ） | 完了した計画、旧チェックリスト |
| `analysis/` | レビュー・分析レポート | UI/UXレビュー、DB設計レビュー |

### `analysis/` ディレクトリの用途

定期的なコード品質レビュー、パフォーマンス分析、設計レビューの結果を保管します。

**保管対象:**
- UI/UXレビュー結果
- データベース設計レビュー
- パフォーマンス分析レポート

**アーカイブ基準:** 3ヶ月以上参照されていない分析は `history/` に移動

## 古いドキュメントの扱い

### アーカイブする基準

以下の場合、`_docs/history/`に移動：

- 6ヶ月以上参照されていない
- 実装が削除された機能のドキュメント
- 古いアーキテクチャの説明

### 削除する基準

以下の場合、ドキュメントを削除：

- 完全に間違った情報
- 既に別のドキュメントで置き換えられている
- プロジェクトに無関係になった

## ドキュメントテンプレート

### decisions/（設計判断）

```markdown
# [判断タイトル]

**作成日:** YYYY-MM-DD
**最終更新:** YYYY-MM-DD

## 背景

なぜこの判断が必要だったのか。

## 検討した選択肢

1. 選択肢A - 概要、メリット、デメリット
2. 選択肢B - 概要、メリット、デメリット

## 最終判断

選択した選択肢とその理由。

## トレードオフ

この判断によるトレードオフ。

## 関連ファイル

- `path/to/file.py:123-456` - 実装箇所

---

**最終更新:** YYYY-MM-DD
```

### features/（機能実装）

```markdown
# [機能名]

**作成日:** YYYY-MM-DD
**最終更新:** YYYY-MM-DD
**ステータス:** 実装完了 ✅ / 実装中 🚧 / 計画中 📋

## 目的

なぜこの機能が必要なのか。

## 実装内容

何ができるのか、どのように実装したか。

## 技術的なポイント

実装時の注意点、工夫した点。

## リスク

既知の問題、今後の改善点。

## 関連ファイル

- `path/to/file.py:123-456` - 実装箇所

---

**最終更新:** YYYY-MM-DD
```

## 定期レビュー（任意）

以下の頻度でドキュメントをレビューすることを推奨します：

- **3ヶ月ごと**: _docs/の内容が最新か確認
- **6ヶ月ごと**: 古いドキュメントをhistory/に移動
- **1年ごと**: history/の不要なドキュメントを削除

ただし、**コード変更時の同時更新**を徹底していれば、定期レビューは不要です。
