# _docs - プロジェクト知識蓄積ディレクトリ

このディレクトリは、プロジェクトの設計判断、実装記録、PLC特有の知見を体系的に蓄積するために使用します。

## 主な読者

- **Claude Code**: コンテキストとして活用（CLAUDE.mdから参照）
- **未来の自分**: 数ヶ月後に設計意図を思い出すため
- **新しい開発者**: オンボーディング時の学習資料として

## ディレクトリ構成

### `decisions/` - 設計判断・思考過程

設計時に迷った点、却下した案、最終的な判断理由を記録します。

**記録内容:**
- なぜこの技術を選んだのか
- どんな代替案を検討したのか
- 判断の根拠（パフォーマンス、保守性、コストなど）
- 制約条件や前提条件

**ファイル例:**
- `socketio-threading-mode.md` - Socket.IOでthreadingモードを選んだ理由
- `equipment-identification-strategy.md` - 設備識別の優先順位設計
- `data-archiving-strategy.md` - 階層化アーカイブシステムの設計思想

### `features/` - 機能実装の記録

新機能の追加・改修の目的と背景を記録します。

**記録内容:**
- 実装目的（なぜこの機能が必要だったのか）
- 機能概要（何ができるのか）
- 技術的な実装ポイント
- リスクと完了条件
- 関連ファイル

**ファイル例:**
- `codex-auto-review.md` - Codex自動レビュー機能
- `local-buffering.md` - ローカルバッファリング機能
- `realtime-monitoring.md` - リアルタイムモニタリング機能

### `plc-knowledge/` - PLCプロジェクト特有の知見

PLCシステム開発で得た知見、トラブルシューティング方法を記録します。

**記録内容:**
- PLCプロトコル（Modbus、FINS、MC Protocol）の実装ノウハウ
- エンディアン問題の対処法
- タイムアウト設定の根拠
- ラズパイデプロイ時のトラブルシューティング
- PLC通信セキュリティのベストプラクティス

**ファイル例:**
- `protocols.md` - PLCプロトコル実装ガイド
- `endianness.md` - エンディアン問題と対処法
- `timeout-settings.md` - タイムアウト設定の考え方
- `troubleshooting.md` - よくある問題と解決策

### `history/` - 過去の実装・改善記録

既存のIMPROVEMENTS.md、INTEGRATION_SUMMARY.mdなど、過去の実装記録を保管します。

### `testing/` - テスト関連ドキュメント

E2Eテスト、Playwrightテストの実装記録やテスト戦略を記録します。

**記録内容:**
- テストシナリオ
- テスト環境のセットアップ手順
- CI/CD統合方法

**ファイル例:**
- `e2e-deployment-test.md` - E2Eデプロイメントテスト

## ドキュメント作成ガイドライン

### 1. 簡潔に書く

Claude Codeがコンテキストとして読み込むため、冗長な説明は避ける。
- ❌ 悪い例: 「この機能は非常に重要で、多くの検討を重ねた結果、最終的に...」
- ✅ 良い例: 「目的: オフライン時のデータロス防止。選択: SQLiteベースのローカルバッファ。根拠: 軽量、トランザクション対応。」

### 2. 具体的なファイルパス・行番号を記載

関連コードの場所を明示する。
- 例: `plc-dashboard/backend/api/routes.py:388-432` - 設備登録ロジック

### 3. コード例を含める

重要な設計パターンはコード例で示す。

### 4. 更新日を記載

各ドキュメントの冒頭に作成日・更新日を記載する。

