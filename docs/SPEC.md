## 1. 製品の目的とスコープ

工場内LAN（イントラネット）で稼働する PLC データの収集・監視・分析システム。

### 用途（2つを両立させる。2026-07-12確定）

1. **運用監視・トレンド** — 現場のリアルタイム見える化（主用途）。
2. **インシデント追跡（トレーサビリティ）** — **エラー/アラームが起きたものを後から追える**こと。全生データを長期保存するのではなく、**エラー/アラームと、その前後の生データ文脈を長期保存**して、稀な異常だけを後から再現・調査できるようにする（§5.2）。

### 物理構成（1機械 = 1PLC = 1Raspberry Pi。2026-07-12確定）

各機械にPLCを取り付け、そのPLCに専用のRaspberry Piを1台取り付けて収集・管理する。したがって **設備の単位は「機械 = PLC = Pi」の1:1:1** であり、これは業界一般の「1ゲートウェイで複数PLC」構成をあえて採らない設計判断（機械ごとの障害分離・配線/設置の単純化・現場での対応容易性を優先）。

### 規模の想定（仕様として確定）

| 項目 | 値 | 備考 |
|---|---|---|
| 設備（PLC + Raspberry Pi） | **最大200台** | 1機械=1PLC=1Pi（上記） |
| 中央サーバー | **1台**（Windows PC） | 冗長化はスコープ外 |
| 同時閲覧クライアント | **10〜20台** | ブラウザアクセス。インストール不要 |
| データ収集間隔 | **既定5秒**（設備ごとに1〜60秒で設定可） | 200台×5秒 = 平均40件/秒の受信 |

### スコープ外（明示的にやらないこと）

- インターネット経由のアクセス、クラウド連携
- 中央サーバーの冗長化・クラスタリング
- PLCへの書き込み制御（READ_ONLY_MODE 維持。監視専用）

## 2. システム構成

```
[PLC ×200] ←Modbus/FINS/MC/S7→ [Raspberry Pi ×200: 収集エージェント]
                                      │ HTTP POST（APIキー認証）
                                      ▼
[中央サーバーPC ×1]  ← Windowsサービスとして常駐（PC起動と同時に稼働）
  ├─ PostgreSQL（同梱）
  ├─ Flask API + Socket.IO（認証必須）
  ├─ Nuxt ダッシュボード配信
  └─ Electron トレイアプリ（サービスの「顔」: 状態表示・起動停止・画面表示）
                                      │ ブラウザ / Socket.IO（設備別room）
                                      ▼
[閲覧クライアント ×10〜20]  ← ブラウザのみ。ログイン必須
```

## 3. 配布形態

### 3.1 中央サーバー（パソコン側）

**「見た目はデスクトップアプリ、中身は常駐サービス」方式。**

- 配布物は **Windowsインストーラー1本（.exe）**。実行すると:
  1. PostgreSQL（ポータブル版）・Flask・Nuxt静的ビルドを配置
  2. これらを **Windowsサービスとして登録**（PC起動と同時に自動開始、ログオフ・アプリ終了で止まらない）
  3. デスクトップとタスクトレイに Electron 製の管理アプリを配置
- **Electron トレイアプリの役割**（サーバー本体ではない）:
  - ダブルクリックでダッシュボードを表示
  - サービスの稼働状態表示・起動/停止/再起動
  - ログ閲覧、バックアップ実行
  - **ユーザー管理のadmin画面**（ユーザー追加・無効化・パスワードリセット。§4.1参照。サーバーPCの前にいる人=物理アクセスを持つ管理者だけがユーザー管理できる、という整理）
- 開発環境は引き続き Docker Compose（`docker-compose.yml`）。本番はサービス、開発はDocker、と役割を固定する。

**既存コードとの対応:**
- `electron/`（Docker管理GUI）→ トレイアプリとして発展（Docker操作をサービス管理に差し替え）
- `desktop-app/` → Postgresポータブル同梱・起動シーケンスのノウハウをインストーラーに吸収し、**ディレクトリとしては廃止**（`desktop-app/src/` の独自UIは未使用のため削除）
- バックエンド起動経路は **`wsgi.py` に一本化**。`flask run` は開発専用、`manage.py` 直接起動は廃止
  - 本番WSGIサーバは **Waitress + Socket.IOのlong-polling固定（WebSocket不使用）**。WaitressのWebSocket非対応は確定事項だが、long-pollingなら動作し `async_mode='threading'` と整合する。
  - **【2026-07 負荷検証で確定・当初案から変更】** 単一プロセス構成は不合格だった。閲覧クライアントのlong-pollingがエージェントのingestを巻き込み**スループット崩壊**（分離なし14 req/s・p95=22秒。threads64でも無改善。Waitressの単一asyncore I/Oスレッド起因）。gevent系への切り替えではなく、**ingest/viewer の2プロセス分離＋Redis(`message_queue`)共有**で解決（ingest 279 req/s・p95=74ms・配信100%、threadingモード維持）。ingest側の配信emitはRedis経由でviewer側クライアントへ届く。詳細は `_docs/decisions/wsgi-serving-load-verification.md`。小規模（閲覧数台）では `SOCKETIO_MESSAGE_QUEUE` 未設定の単一プロセスでも可
- PostgreSQL同梱はライセンス上問題なし（PostgreSQLライセンス・コピーレフトなし、2026-07調査で確認）。ただしインストーラーの `initdb` 実行時に `--auth`（デフォルトのtrustを避ける）・`--encoding=UTF8`・`--locale` を必ず明示する
- サービス登録ラッパーは **NSSM を第一候補**（自動再起動・ログローテーション等が公式ドキュメントで裏付け済み、Grafana公式案内実績あり）。PostgreSQLは `pg_ctl register` で自前登録するためラッパー対象はFlask側のみ。
  - **【2026-07-12 再評価】** NSSMは最終リリース2017で実質放置。維持されている代替として **Shawl**（Rust製・winget導入可・保守中）、WinSW（保守モード）、Servy（新興）がある。NSSMでも動作するが greenfield では **Shawl を有力代替**として実サービス化(Phase 4)時に比較検討する

### 3.2 Raspberry Pi 側（200台のフリート管理）

- **初期セットアップ**: セットアップ済みSDカードイメージを標準配布物とする（イメージ焼き→設備固有設定はWebUIまたは中央サーバーから）
- **設定配布**: PLC接続設定・データ項目設定は中央サーバーのDBが正。エージェントは起動時と定期的にサーバーから設定を取得（現状の `config_manager.py` のDB優先方式を正式仕様化）
- **プログラム更新**: 当面は手動更新を許容しつつ、エージェントがバージョンを `/api/register` で申告し、**サーバー側で全200台のバージョン・死活を一覧できる**ことを必須とする

## 4. 認証・セキュリティ

**方針: イントラネット前提でも「無認証」は廃止。全経路を認証で固める。**

### 4.1 ユーザー認証（ブラウザ → サーバー）

- バックエンド実装のトークン認証。**フロント埋め込みの資格情報は全廃** ✅ 実装済（**DB保存の不透明Bearerトークン方式**を採用。JWTではなく失効管理しやすい不透明トークンにした。`_docs/decisions/auth-architecture.md`）
- ロールは2つ:
  - **admin**: 設備設定の変更、ユーザー管理、データ削除・クリーンアップ
  - **operator**: 閲覧＋現場操作（アラーム確認・解除、エラー解決）
- **全ページ・全APIを保護対象**とする（現状の「2ページのみ保護」を廃止）
- 初期パスワードは初回セットアップ時に強制変更
- **ユーザー管理（追加・無効化・パスワードリセット）は中央サーバーPC上のトレイアプリ内admin画面で行う**（2026-07-09決定。§3.1参照）。閲覧クライアントのWeb UIにはユーザー管理画面を置かない（サーバーへの物理アクセスを管理の前提にする）
  - トレイアプリが完成するまでの間（Phase 1〜3）は、サーバーPC上のCLI/セットアップスクリプトで代替する

### 4.2 エージェント認証（Raspberry Pi → サーバー）

- `POST /api/register`・`POST /api/logs`・エラー/アラーム報告に **APIキー（HTTPヘッダ）** を必須化
- **スキーマとキー検証ロジックは最初から設備別キー対応で実装し、運用は共有キー1本で開始する**（2026-07-09決定）。具体的には: キー管理テーブルの設備紐付けをnullable（null=全設備共有キー）とし、設備別への移行はコード変更なしの運用判断にする。キーはハッシュ化して保存し、サーバー側で発行・失効管理

### 4.3 その他

- `SECRET_KEY`・DB パスワードの弱いデフォルト値を廃止（インストーラーが生成）
- APIエラーレスポンスに内部例外文字列（`str(e)`）を含めない

## 5. データ仕様

### 5.1 動的データ項目（一気通貫で実装する）

**「設備ごとに任意のデータ項目を定義できる」を中核仕様として完成させる。**

- `PLCDataConfig`（項目名・アイコン・単位・PLCアドレス・型・倍率）で項目を定義 — 既存
- 収集エージェントは定義された全項目を読み取り送信 — 既存
- **受信APIは全項目を `Log.data`（JSON列）に保存する** — 現状欠落。固定6カラム（温度・電流等）は後方互換として並存
- **配信・履歴API・シリアライザ・画面表示も `data` を含める** — 現状欠落
- 日次/月次集計は `data_summary`（JSON）に全項目の avg/max/min を持つ — 受け皿は既存、集計ロジックに配線
- 項目名のバリデーションはホワイトリスト方式をやめ、**形式検証（文字種・長さ）** に変更（任意項目を許すため）

### 5.2 収集間隔と保持期間（段階的・イベント駆動。2026-07-12再設計）

**設計原則:** 全生データを長期保存するのは200台規模ではPC1台で非現実的（200台×5秒＝約1.0億行/30日）。よって**運用監視は短期の生データ＋長期の集計**でまかない、**トレーサビリティは「エラー/アラームとその前後の生データ文脈」だけを長期保存**することで両立する。産業ヒストリアンが圧縮(swinging door等)で生を1-5%に落として2-5年持つのに対し、本システムは**無圧縮＋イベント駆動アーカイブ**で同等の目的を達成する。

| データ | 保持期間 | 目的・根拠 |
|---|---|---|
| 生ログ（全量） | **30日** | 運用監視・トレンド。月単位パーティショニングで1台のPCで現実的な上限 |
| 日次集計 | 365日 | 中期トレンド（avg/max/min） |
| 月次集計 | 永続 | 長期トレンド |
| エラーログ / アラーム | **1年（設定で延長可）** | インシデント追跡。現行30日は「後から追える」に短いため延長。稀なイベントのため長期保存してもストレージ負荷小 |
| **★エラー/アラーム前後の生データ文脈（±数分の窓）** | **1年（エラー保持と同期。設定で延長可）** | **新機構**。エラー発生時の値の推移を後から再現・調査するため、該当設備の生ログを±数分だけ切り出して長期保存する。30日で生バルクが消えても、過去のインシデントは調査可能 |

- `logs` テーブルは **月単位パーティショニング** を導入（クリーンアップはDELETEではなくパーティションDROPに変更 → 高速・断片化なし）※実装済み
- **エラー文脈の保全（新規実装項目）:** エラー/アラーム記録時に、該当 `equipment_id` の発生時刻±N分（既定±5分・設定可）の生ログを別テーブル（例 `incident_context`）へコピーする。生バルクのパーティションDROPの影響を受けない長期保存領域とする。まずはエラー記録フックでの同期コピーで実装し、負荷が問題なら非同期化を検討
- 集計・クリーンアップのスケジューラは **独自threadingスケジューラ（`api/scheduler.py`）に1系統統合済み**（当初案のAPScheduler化は、依存追加の必要性が低く現行実装で要件を満たすため見送り）

### 5.3 PLC通信原則（2026-07の一次情報再調査を反映）

- **32bit値のワード順序（word_order）はメーカー・機種依存**とし、設備または項目ごとに設定可能にする（`high_first` / `low_first`。既定値はメーカープロファイルから導出）
  - 旧原則「全PLCで Big-Endian・`(word1<<16)|word2` 固定」は三菱の公式マニュアルで反証済み（三菱は先頭アドレス=下位ワード → `low_first`）。シーメンスS7は `high_first` で確定。オムロン・キーエンスは実機確認必須
  - word_order 設定の導入は Phase 2（動的データ項目）と同時に実装し、現行 `convert_plc_data` の固定処理を置き換える
  - 新規メーカー・機種の接続時は、既知の32bit値で実PLC表示と突き合わせる受け入れ手順を必須とする
- 接続タイムアウト5秒 / 読取タイムアウト3秒。**ただし設定は各ライブラリの正規APIで行う**（pymcprotocolは `connect()` にtimeout引数がなく `setaccessopt(timer_sec=5)` を使う。未設定時の実デフォルトは監視タイマ1秒/ソケット2秒であり、現行実装はこの状態）
- 読み取り専用（書き込み禁止）
- 送信失敗時はSQLiteローカルバッファに保持し再送（保持7日・60秒間隔・上限10回）

## 6. リアルタイム配信

- Socket.IO の配信を **設備別room（`equipment_{id}`）宛て** に変更。監視画面は表示中の設備のみ購読（join の仕組みは実装済み、配信側を変更）
- 全体ブロードキャスト（`monitoring` room）は設備一覧のステータス更新など軽量イベントのみに限定
- `async_mode='threading'` は当面維持（200台×40msg/秒 + 20クライアントの規模なら許容）。性能問題が実測されたら見直す
- **本番のSocket.IOトランスポートはlong-polling固定（WebSocket不使用）**（§3.1のWaitress採用とセット。5秒間隔のデータ更新にWebSocketは必須でないという判断）
- **【2026-07 確定】** 高負荷時は ingest/viewer 2プロセス分離＋Redis(`message_queue`)共有で配信する（§3.1参照）。ingest側emitはRedis経由でviewer側の設備別roomへ届く

## 7. 対応PLC

**4メーカー全対応を正式仕様とする。**（対応条件は2026-07の一次情報再調査に基づく）

| メーカー | プロトコル | 状態・条件 |
|---|---|---|
| 三菱 | MC Protocol (3E) | 実装済み。pymcprotocolの実機テスト済みは3Eのみ。word_order=`low_first` |
| オムロン | FINS (UDP) | 実装済み。**CP1/CJ系が対象**。NX/NJ系はFINS大幅制限（公式非推奨・CJ互換メモリのみ・要事前設定）のため、本格対応はEtherNet/IP (CIP) ドライバ追加を将来課題とする |
| キーエンス | MC(SLMP)互換 / Modbus TCP | 実装済み（条件付き）。**MC(SLMP)互換読み取りを第一候補とし、Modbus TCP（KV-XLE02拡張ユニットのサーバ機能）はフォールバック**（2026-07-09決定）。SLMPが実機で読めれば三菱ドライバを流用しキーエンス専用ドライバの保守を削減できる。実機検証はSiemens検証と同時期（Phase 5）に実施 |
| シーメンス | S7 (python-snap7 3.x) | **スタブ → 実装する**。開発中はSnap7 server demo（無料のソフトウェアサーバ）で検証し、**リリース判定前にS7-1200実機（エントリーモデル）を1台調達して前提条件手順書ごと最終確認**（2026-07-09決定。PUT/GET許可・最適化ブロックアクセス無効化はシミュレータでは再現されないため） |

**シーメンス実装の前提条件（仕様として明記）:**
- **python-snap7 >=3 を採用（Pure Python。C共有ライブラリ・コンパイラ不要。ARM/Alpine可）**。2026-07-12に一次情報で確認済（v3.0でS7スタックを純Python実装。`<3` はCラッパーなので **`>=3` のバージョンピンを必須**とする）
- S7-1200/1500はPLC側設定が必須: ①PUT/GET通信許可、②対象DBごとの「Optimized block access」無効化。**②はDB値の初期化を伴うため、セットアップ手順書に「コミッショニング時に実施」と明記する**
- rack/slot: S7-1200/1500=0/1、S7-300=0/2、S7-400=構成依存。S7-200/LOGO!はTSAP指定（初期スコープ外とする）
- S7のデータ本体はBig-Endian（word_order=`high_first`）

- 実PLC接続失敗時のダミーデータ自動フォールバックは**本番では無効化**（設定フラグ化）。障害が「それらしいデータ」で隠れるのを防ぐ
